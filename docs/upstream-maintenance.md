# 本家更新への追従

CLIは `internal/cli/` に置き、本家のTUIの状態管理には依存させない。
通信は `internal/http` と本家採用のArikawaを再利用し、CLI専用の通信実装を複製しない。
認証は `internal/auth` のキーチェーンをTUIと共有する。

## 接続箇所

| ファイル | 独自変更の役割 |
| --- | --- |
| `cmd/root.go` | TUI起動前のCLIコマンド振り分け |
| `main.go` | CLIの終了コード反映 |
| `internal/ui/root/token.go` | 共通認証ストアの利用 |
| `internal/ui/root/model.go` | 共通の環境変数名の利用 |
| `internal/ui/chat/model.go` | トークン更新ハンドラーを1行で登録 |
| `internal/ui/chat/token.go` | 更新トークンを共通ストアへ保存 |

新しいCLI機能は原則として `internal/cli/` に追加する。
画面ごとのモデルへのCLI分岐や、TUIのキャッシュへの依存を増やさない。
既存APIクライアントを直接利用する現在の構成を維持し、大きな抽象化や別リポジトリ化は行わない。

## ログイン修正とCLI追加の区別

本家との差分にはCLI以外の変更も含まれる。更新時に独立して判断する。

| コミット | 目的 | 本家更新時の確認 |
| --- | --- | --- |
| `b87220c` | CLI追加・認証共有 | CLIの接続箇所と動作テストを確認 |
| `0789317` / `f22777e` | パスワード・QRログインのCAPTCHAエラー表示 | 本家に同等の対応があれば独自対応の撤去を検討 |
| `83db639` | QRの診断ログと意図した接続終了の扱い | 接続終了の修正は動作変更なので、ログと一緒に機械的に削除しない |
| `f2edb74` | 起動バイナリとログイン方式の診断ログ | 本家のログ変更と照合し、必要性を個別に判断 |
| `f0a147d` / `41504dd` / `a7e775b` | CLI認証・ユーザートークン対応・利用手順 | CLI側の変更として維持 |

既存コミットの履歴は書き換えない。今後もCLI機能、ログインの動作修正、
一時的な診断ログは別々のコミットにする。本家側に修正が入った場合は、
該当する独自差分だけを比較して削除・調整する。

## 自動チェック

`.github/workflows/upstream-compatibility.yml` は毎日、`main` へのpush時、
手動実行時に、本家 `main` をActionsの使い捨てチェックアウトへ仮マージする。
マージが衝突すればその段階で失敗する。マージ成功後は本家更新後の `go.mod` で
Goを選択し、全体のrace付きテストを通常構成と軽量構成で実行してビルドする。
ブランチへのpushや自動マージ、Issue・PRの作成は行わない。

フォークでは定期実行が無効の場合があるため、GitHub Actionsでワークフローを有効にする。
失敗はActionsの実行結果で確認する。通常のCIも引き続き利用する。

テストはローカルHTTPサーバーとメモリー内キーチェーンを使い、実際のDiscordや
OSの認証情報を操作しない。各コマンドのGET先・クエリ・認証ヘッダー・JSON出力、
メッセージの順序とページング、認証・権限・引数エラーの終了コードを確認する。
両HTTP構成で同じテストを実行する。Discord側の仕様変更や実アカウントの権限は
このテストでは判定できないため、必要な更新時には別途実通信を確認する。

## 更新を取り込む手順

1. 作業ツリーを確認し、作業中の変更を保護する。
2. `git fetch upstream` で本家を取得し、更新内容を読む。
3. 作業用ブランチで `git merge upstream/main` を実行する。
4. 上の接続箇所とログイン関連差分を確認し、衝突を解決する。
5. `go test -race ./...` と
   `go test -race -tags no_spoof_tls_fingerprint,no_voice,no_syntax_highlighting ./...`、
   `go build .` を実行する。
6. 必要に応じてCLIの実通信とTUIログインを確認してから、取り込み結果を採用する。
